# フィールド追加 UI 拡張プラン

`FieldAddPanel` / `FieldGroup`（Admin Root の composable 編集）の拡張・用語整理メモ。

> **SPEC.md について:** 開発当初の要件として凍結済み。本プランの内容は SPEC を編集せず、本ファイルを正とする。

## 用語（確定）

本CMSの呼称は次の6語に統一する。

| 概念 | 呼称 | 例 |
|------|------|----|
| まとまり（1つの構造単位） | **フィールド** | `hero`、`card` |
| フィールドの名前（フィールド自体を指すときも使う） | **フィールドネーム** | `hero` |
| 中身：1行テキスト | **フィールドタイトル** | |
| 中身：本文テキスト（プレーン / リッチ装飾） | **フィールドテキスト** | |
| 中身：画像（URL・代替テキスト・リンクを内包） | **フィールドイメージ** | |
| 中身の総称／API に出力される実際のキー | **フィールドパス** | `hero.title`、`hero.image.url` |

- 「フィールドパス」は、特定の中身に限定せず**総称**として使う場合と、**出力キーそのもの**を指す場合の両方に使う（同一概念を名前側・値側から見たもの）。
- **廃止する語:** 「JSON Path」「Path Name」「prefix」「グループ」「カスタムフィールド」。
- **用語に合わせたコード改名**（コンポーネント名・`data-l`・内部識別子 `prefix` / `jsonPath` 等）は**後回し**。UI 文言の整理はプラン 1 と並行可。

> 補足: フィールドタイトル,フィールドテキストはプレーン / リッチ（HTML 保存・サニタイズ済み）を選べる。
> フィールドイメージ 1つは `image.url` / `image.alt` / `href` の複数フィールドパスを生む。
> フィールド内の並び（タイトル → テキスト → イメージ）は CMS 側固定。交互配置はフロント責務（プラン 3）。

## 背景・痛点

現状は「フィールドネーム＋中身」を**ネストした JSON オブジェクト**として保存する仕組み。

- 1フィールド = `hero.title` / `hero.text` / `hero.image.url` … → 保存 JSON は `{ "hero": { "title": "...", "image": { "url": "..." } } }`
- 1フィールドは「テキスト1・画像1」程度が上限。
- 「横並び 3 枚カード」「カード内に画像複数」を作ると、フィールドを手作業で量産する必要がある。
- フィールドネームに `card.0` 等は書けるが、これはオブジェクトのキー `"0"` で**本物の配列ではない**。

連番スカラーキー（`image1` `image2` …）案は件数の発見・追加削除時の番号振り直しで脆い。
よって**フィールドの繰り返し（配列）化**で解決する。

---

## 構造の解説（プラン 1 と プラン 2 の違い）

### 複製の連番（プラン 1）と配列のインデックス（プラン 2）は別物

どちらも数字が付くが、**JSON の形が根本的に違う**。

#### プラン 1：複製 ＝ 別フィールドを増やす（オブジェクトが兄弟になる）

`hero` を複製すると、フィールドネームに **2 桁連番**が付いた**別フィールド**ができる（例: `hero01`）。

```json
{
  "hero":  { "title": "メイン", "text": "..." },
  "hero01": { "title": "メイン", "text": "..." }
}
```

- 連番は **フィールドネームの一部**（JSON の**トップレベルキー**が増える）。
- 用途: 横並び 3 枚カードを、配列化前の**暫定・最小差分**手段として素早く作る。
- 複製時は**入力値・format（plain / richText）をコピー**し、複製した時点で本物のデータパスが生える。

#### プラン 2：繰り返し ＝ 1 フィールドの中身が配列になる

`cards` に「繰り返し」を付けると、**同じフィールドネーム 1 つ**の値が配列になる。

```json
{
  "cards": [
    { "title": "カードA", "text": "..." },
    { "title": "カードB", "text": "..." }
  ]
}
```

- 数字は **配列のインデックス**（`0`, `1`, `2` …）。フィールドネームは `cards` のまま。
- 用途: 件数可変・要素の追加削除が自然な本命モデル。

#### フィールドパス上の「数字」の位置（重要）

数字の付き方は**プラン 1 とプラン 2 で位置が違う**。タイトルの**後ろ**に付くわけではない。

```txt
プラン 1（複製）     hero01 . title
                     └─フィールドネーム─┘   └─中身─┘
                     連番はネーム末尾

プラン 2（配列）     cards . 0 . title
                     └ネーム┘   └─中身─┘
                     インデックスはネームと中身の間
```

| 種類 | 例 | 数字の意味 |
|------|-----|-----------|
| 複製連番 | `hero01.title` | `01` = フィールドネーム `hero01` の一部 |
| 配列インデックス | `cards.0.title` | `0` = 配列 `cards` の 1 件目（**title の後ではない**） |

`cards.title.01` のような形には**ならない**。

#### composableFieldFormats との関係

リッチ / プレーン指定は `schema_json.composableFieldFormats` に **フィールドパス → format** で保存される（例: `"hero.title": "richText"`）。

| 操作 | composableFieldFormats に増えるキー例 |
|------|--------------------------------------|
| `hero` を複製 → `hero01` | `"hero01.title": "richText"`（**複製時に 1 回コピー**。以降は親子同期しない） |
| `cards` 繰り返しフィールド | `"cards.*.title": "richText"`（**テンプレート 1 キー**。要素追加で行を増やさない） |

**複製の連番**は「別フィールド用の新しいパスを丸ごとコピーする」話。
**配列のインデックス**は「同じフィールド内の何番目の要素か」を指す話。
混同しやすいが、JSON 上では前者はキーが増え、後者は 1 キーの配列長が変わる。

#### format と「親子同期」について

- **プラン 1（複製）:** 複製ボタンを押した**瞬間だけ** format をコピーする。あとから元を rich に変えても `hero01` は追従しない。**親子紐づけは持たない**（独立した別フィールドとして扱う）。
- **プラン 2（配列）:** 要素ごとに format を変える必要はない。現行 UI は行ごとに plain / rich を切り替えられるが、配列化時は **フィールド定義（テンプレート）に 1 つだけ**トグルを置き、全要素に同じ format を適用する。`composableFieldFormats` は `cards.*.title` のようなワイルドカード 1 キーで足りる。

## 実行プラン

### 1. フィールドの複製（実装予定 / 最優先・最小差分）

- 既存フィールドに複製ボタンを付ける。
- **複製時の挙動（確定）:**
  - 入力値（タイトル・テキスト・画像 URL / alt / href）を**すべてコピー**する。
  - フィールドネームは **ベース名 + 2 桁連番**（区切りなし。`hero01`）。既存と衝突しない最小の空き番号を採用。
  - `composableFieldFormats` も、複製先フィールドパスへ**同内容を 1 回コピー**する（例: `hero.title` → `hero01.title`）。以降の親子同期はしない。
- データ規約・配信 API・フロントは**一切変更しない**。現行モデルのまま。
- 範囲: `FieldGroup`（複製ボタン）＋ `ComposableContentForm`（複製ハンドラ）。

#### 連番付与アルゴリズム（採用案：ベース名抽出）

「オリジナルを複製」と「複製済みを複製」で**同じルール**に統一する。

1. 複製元ネームから **ベース名** を求める  
   - 末尾が `01`〜`99` の 2 桁数字なら、それを除いた部分がベース（例: `hero01` → ベース `hero`）  
   - 末尾に該当数字がなければ、ネーム全体がベース（例: `hero` → ベース `hero`）
2. 画面上の全フィールドネームを走査し、`ベース` または `ベース + 2桁` に一致するものを集める
3. 使用中の番号の最大値 + 1 を 2 桁ゼロ埋め（`01`, `02`, …）して `ベース + 番号` を新ネームにする

**挙動例（同一ページ内）**

| 操作 | 複製元 | 既存ネーム | 新ネーム |
|------|--------|-----------|---------|
| オリジナルを複製 | `hero` | `hero` | `hero01` |
| オリジナルを再複製 | `hero` | `hero`, `hero01` | `hero02` |
| 複製済みを複製 | `hero01` | `hero`, `hero01` | `hero02` |
| 複製済みを複製 | `hero02` | `hero`, `hero01`, `hero02` | `hero03` |

`hero01` を複製して `hero0101` には**ならない**。常にベース `hero` の次番号。

**既知の限界（許容）**

- 意図的に `card10` と名付けたフィールドを複製すると、末尾 `10` を連番とみなしベース `card` になる。稀なケースとしてドキュメント化し、必要なら手動リネームで対応。
- 99 件超は `100`（3 桁）にフォールバックするか、エラーにするかは実装時に決める（通常案件では未到達）。

**将来の代替案（今は不要）**

- 各フィールドに `duplicateFamily: "hero"` のようなメタデータを持たせ、名前解析を使わない方式。ヒューリスティックで問題が出た場合の逃げ道。

### 2. フィールドの繰り返し＝配列化（実装予定 / 本命）

- フィールドに「繰り返し」指定を追加し、`フィールドネーム[]`（本物の JSON 配列）として同じ構成の要素を増減できるようにする。
- 「横並びカード」も「カード内の画像複数」も同じ仕組みで表現。消費側は配列をループするだけ。
- 設計で詰める点:
  - JSON 形状: フィールドを配列にし、各要素は現行 object 構成（`{ title, text, image: { url, alt }, href }`）。
  - 復元: `restoreGroupsFromData` を配列インデックス対応に拡張（`matchKnownSuffix` がインデックス区切りを解釈）。
  - 配信 API / フロント: `data-cms-each="cards"` + テンプレート内相対パス（`data-cms="title"`）が正規。絶対パス `cards.0.title` は開発者向けの例示程度。
  - フィールドテキストの plain / rich 指定: `composableFieldFormats` は **`cards.*.title` 形式のテンプレート 1 キー**。UI の format トグルは配列要素行ではなく**フィールド定義（テンプレート）に 1 つ**。

#### 配列要素の削除（イメージ）

管理画面で `cards`（繰り返しフィールド）に 3 件あるとする。

| UI 上 | 保存 JSON（イメージ） |
|-------|----------------------|
| カードA / カードB / カードC | `"cards": [ A, B, C ]` |
| カードB の「削除」を押す | `"cards": [ A, C ]`（**配列から要素ごと除去**。インデックスは 0 から詰め直す） |
| 下書き保存 | 上記が API に PATCH され、配信 JSON も 2 件になる |

- 「削除」= その**配列要素オブジェクト全体**を消す（中の title だけ空にする、ではない）。
- フロントは `data-cms-each="cards"` で 2 件だけ描画される。
- **最後の 1 件を削除したとき（確定）:** フィールド定義は残す。保存 JSON は空配列 `"cards": []`。UI は 0 件状態で「要素を追加」のみ表示。フィールド自体を消す操作とは別。

#### ネスト配列（用語の意味）

- **1 段の繰り返し（プラン 2 の対象）:** `cards[]` — カードが複数。各カードは title / text / image 1 セット。
- **ネスト配列（プラン 2 初期スコープ外の例）:** `cards[].images[]` — 各カードの**中に画像が複数**。

ネスト配列は「配列の中にまた配列」であり、UI・復元・format・サニタイズが一段複雑になる。**初期実装では `cards[]` の 1 段のみ（確定）**。カード内画像複数はプラン 1 複製 or 将来検討。

### 3. 交互配置（中身を交互に並べる）→ やらない

- フィールドタイトル / テキスト / イメージを**任意順で交互に並べる**ことは CMS では扱わない。
- 並び順・交互レイアウトは **JSON 取得側（フロント）で操作**する責務とする（ヘッドレス原則＝構造化データのみ提供）。

## データ規約イメージ（プラン 2 後）

```json
{
  "cards": [
    { "title": "カードA", "text": "...", "image": { "url": "/a.jpg", "alt": "..." }, "href": "/a" },
    { "title": "カードB", "text": "...", "image": { "url": "/b.jpg", "alt": "..." }, "href": "/b" }
  ]
}
```

消費側（フロント）は `cards` をループし、必要なら並び替え・交互配置を行う。
